## Architectural implications surfaced (not designed — carry into 01-REQUIREMENTS / 02-ARCHITECTURE)

These are new implications this Interview exposed relative to the existing `docs/milestones/problem-department-mvp.md`, recorded explicitly per Danny's instruction rather than silently encoded:

1. **Problem Brief ≠ Opportunity.** Danny explicitly distinguished these: the Brief is evidence produced by one discovery path (Problem Department); Opportunity is the likely shared object multiple discovery paths (Problem Department, Personal Pull, Signal Foundry, others) can eventually produce. This MVP produces Problem Briefs only. Opportunity remains a named future requirement, not a schema.
2. **Approve is not a build trigger.** Approve hands something toward a *future* Opportunity/handoff decision — it does not itself start Prototype Department work. The milestone doc's step 8 ("present for approval/rejection/watch") should be read with this operational meaning in `01-REQUIREMENTS.md`.
3. **Watch conditions are structured but unscheduled for the MVP.** Watch must record explicit, named reconsideration conditions even though no auto-recheck scheduler is built yet — this is a requirement on the data captured, not on runtime behavior, for this slice.
4. **Auditability/versioning is in-scope for the MVP**, not deferred — this is a stronger requirement than the milestone doc's step 9 ("record sources, artifacts, workflow state...") states explicitly; the Interview sharpens it to: claim provenance, Brief versioning, decision-to-evidence-state binding, non-destructive correction, and invalidation tracking.
5. **Multi-channel seed capture (bookmarks, browser history, saved posts, notes app, WhatsApp/Major Tom) is a distinct, real future architecture area** — potentially its own product surface — explicitly out of scope for this slice's input contract, which stays "human submits one or more source artifacts directly."
